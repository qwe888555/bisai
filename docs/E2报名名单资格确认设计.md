## 一、已批准决策（全部定案）

1. **[已批准]** 方案 4b：独立 `RosterQualificationLog` 资格审计表，**不扩展 ReviewRecord**。
2. **[已批准]** 终审子方案 α：无有效人工确认凭证的 `QUALIFIED` 不得通过正式终审（422）；β 豁免方案永久否决，不得借 reason/豁免文字绕过。默认 `qualification_status=QUALIFIED` 不构成确认凭证。
3. **[已批准]** **不实现宽限期**：不增加宽限配置、时间窗口或临时豁免机制。提交与初审阶段可提示未确认状态，但提示不替代人工确认、不绕过终审硬门槛；终审对 `QUALIFIED` 且凭证缺失/无效一律 422（统一错误格式）。
4. **[已批准]** 权限：四操作（CONFIRM/REJECT/EXCLUDE/REVOKE）仅 TEAM+UNIVERSITY，逐请求后端 scope 校验；CITY/PROVINCE_REVIEWER 只读；ADMIN 本期不开放；**不复用 R5**；roster CRUD 的 R5 现状为独立议题，本轮不动。
5. **[已批准]** 凭证与状态机：`confirmed_by`=Account.id；CONFIRM/凭证更新/日志追加同事务；REJECT→DISQUALIFIED 且原因必填；REVOKE 双清凭证+原因必填+日志 append-only；EXCLUDED 不可逆（重新纳入仅走名单编辑，且须重新完成资格确认）；版本冲突 409；终审实时读库、不依赖缓存、不读旧日志判凭证。
6. **[已批准]** **DISQUALIFIED → CONFIRM → QUALIFIED 允许**：有权限操作者重新核实后可直接确认；必须是明确的人工操作，不得系统自动确认；产生新凭证+新确认日志；原驳回记录保留不覆盖；EXCLUDED 不适用（见 5）。
7. **[已批准]** **资格日志 FK 采用 SET_NULL + 冗余名单 ID**：名单记录删除后外键置空，但冗余保存的原始名单 ID 仍可追溯；查询与展示逻辑必须能区分"已删除名单的日志"。**不是 CASCADE**。
8. **[已批准]** API 契约采用 §五草案（实施前按 §五.2 核对既有规范）。
9. **[已批准]** 不联动材料域，不修改 MaterialType 或报名附件门槛（方案 C 衔接）。
10. **[已批准]** 不自动为历史名单补写确认人、确认时间或任何凭证（D4 红线）。

## 二、模型与迁移设计（[已实施-编码完成，迁移未执行]）

### RosterItem 增列
- `confirmed_at` DateTime(null=True, blank=True, db_index=True)
- `confirmed_by` CharField(max_length=64, blank=True, default="")
- 成对读写；服务层以 `confirmed_at is not None and confirmed_by` 双条件判定有效凭证（防单侧脏数据）；REVOKE 双清。

### RosterQualificationLog 新表
- `id` CharField(64) 主键（rstql_ 前缀）；
- `roster_item` FK **null=True, on_delete=SET_NULL**；
- `roster_item_id_snapshot` CharField(max_length=64)——冗余原始名单 ID（SET_NULL 后追溯依据；[实施前核对] 命名对齐项目既有"冗余 ID"惯例，如有）；
- `athlete_id` CharField(64, blank=True, default="")——建议随日志记录，进一步提升删除后可读性（[实施前核对] 与 RosterItem.athlete_id 类型一致）；
- `action` choices（CONFIRM/REJECT/EXCLUDE/REVOKE）；`reason` TextField(blank)；`operator_account_id` CharField(64)；继承 VersionedModel；
- append-only：无 update/delete API，服务层仅 create；
- 索引：`(roster_item, -created_at)` + `roster_item_id_snapshot` 单列（追溯查询）；
- **ReviewRecord 零改动**；
- 查询/展示约束：日志关联名单已删除（FK 置空）时，展示层以 `roster_item_id_snapshot` 标识并标注名单已删除，不得因 FK 为空而丢弃记录。

### 迁移
- `enrollments/0003`：AddField×2 + CreateModel（含 SET_NULL FK 与冗余列），依赖 0002（已应用），与阶段四三迁移（attachments 0002/persons 0003/teams 0002）无交叉依赖，可同批 **[待实施授权，执行与编码分离]**。
- 回滚：RemoveField×2 + DeleteModel——丢当前凭证与资格历史（附注记，模式同 persons/0003）；SET_NULL 不影响回滚复杂度。

## 三、终审与服务层设计要点

- `double_track_issues` 既有"非 QUALIFIED → ERROR"分支后新增：`QUALIFIED 且无有效凭证` → `QUALIFICATION_NOT_CONFIRMED` 422（项目统一错误格式）；EXCLUDED 维持排除不查（五点 exclude 语义不动）。
- 无宽限逻辑：终审层不存在任何豁免分支。
- 状态机：CONFIRM（非 EXCLUDED；幂等 no-op；DISQUALIFIED 可直接 CONFIRM——[已批准]）；REJECT=DISQUALIFIED（reason 必填，缺→422 BUSINESS_VALIDATION_FAILED，与实现一致）；EXCLUDE（reason 必填；不可逆，资格操作层四操作均 409）；REVOKE（仅 QUALIFIED+有效凭证；reason 必填；双清凭证；状态值保持 QUALIFIED 但凭证失效——终审读凭证非状态值）。
- 终审后禁令（D-2，[已批准] 2026-10-29 实施）：`enrollment.status == APPROVED` 时 CONFIRM/REJECT/EXCLUDE/REVOKE 全部 409 STATE_CONFLICT（结构化原因 `ENROLLMENT_APPROVED`），禁令优先于幂等 no-op，被拒操作不产生日志/不改凭证；**REJECTED/WITHDRAWN 不纳入禁令**（重审场景保留现状）；服务层读链判断 + 事务内 enrollment 行锁复判双层实施（锁序 enrollment→roster_item，与终审 approve 链相容）。
- 换人审计（D-1，[已批准] 2026-10-29 实施）：rosterUpdate 的 audit 摘要在 athleteId 实际变化时记录 `修改名单条目 athleteId={old}→{new}（资格凭证已失效）`，未变化保持"修改名单条目"；**审计落库仍为响应后写入，非事务原子（既有边界保留）**，仅成功路径有审计声明。

## 五、API 契约（[已批准] 采用草案；[实施前核对] 既有规范）

### 5.1 契约
- `PUT /api/v1/enrollments/{enrollment_id}/players/{roster_id}/qualification`
- 请求：`{action: CONFIRM|REJECT|EXCLUDE|REVOKE, version: int(必填), reason: REJECT/EXCLUDE/REVOKE 必填、CONFIRM 不需要}`
- 响应：`{qualificationStatus, confirmedAt, confirmedBy}`
- 名单列表输出与错误响应沿用项目既有接口规范，不另立第二套格式。

### 5.2 实施前契约核对清单（[实施前核对]，只核对不修改代码）

3. 列表接口是否适合增加资格字段；若加，采用现有字段命名（camelCase）与空值约定；
4. 422/403/404/409 响应结构与错误码符合项目统一 envelope/errors 规范；
