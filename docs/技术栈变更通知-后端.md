# 后端技术栈变更通知（Spring Boot 3 → Django + django-ninja）

发文：成员2（后端总负责人）
日期：2026-10-21
发送范围：成员1（组长·前端）、成员3、成员4、成员5、成员6
状态：已生效（2026-10-21 版本决策：Django 5.2 LTS，已在基线上验证通过）

## 一、结论（一句话）

后端实现技术栈由原定的 **Spring Boot 3 + Maven + JDK17** 变更为
**Django 5.2 LTS + django-ninja 1.3（Python 3.10）**；数据库 MySQL（本地开发默认 SQLite，零依赖启动），
缓存 Redis，文件 MinIO，部署 Docker Compose。
**对外接口契约（路径、请求/响应、错误码、分页字段、角色权限）完全不变**，各成员已设计的接口不用重做。

> 说明：本通知包含两次变更，最终以此为准 —— 先由 Spring Boot 3 变更为 Python 后端，随后技术选型定为 Django + django-ninja。
> 两次变更都只改「怎么实现」，不改「实现什么」；`docs/后端接口文档.md` 一个字都不动。
> 基线骨架来源：成员上传的 django-ninja 模板，已按本项目契约改造并入 `backend/`（模板目录已从仓库移除），
> 因此本次选型与模板同源，后续照 `backend/apps/accounts` 的写法抄即可。

## 二、为什么用 django-ninja

1. 团队课程学的是 Python 后端，Java/Spring 生态不在教学范围内。分工表《风险与砍法》写明「没有可复用的后台脚手架，10 天不成立」，让全员同时学 Java 生态 + 脚手架风险过高。
2. Django 是「电池已装好」的框架：ORM、迁移、缓存、日志、测试开箱可用；`django-ninja` 在其上提供类型化路由与自动 OpenAPI，正好补齐接口层。
3. `django-ninja` 用 pydantic 做请求校验、用 `Router` 声明路由、用 `Schema` 声明出入参，写法比 DRF 更直白，新人上手成本更低；`/api/v1/openapi.json` 可直接导入 Apifox。
4. 与模板同源：模板本来就是 django-ninja 结构，我们只做「按契约改造」，不需要从零搭脚手架。

## 四、能力对照表（Spring 生态 → Django + django-ninja）

| 原方案（Java） | 现方案（Django + django-ninja） | 位置 |
| --- | --- | --- |
| Spring AOP 审计日志 | `AuditMiddleware` 中间件 | `apps/common/middleware.py` |
| Bean Validation | pydantic `StrictSchema`，未知字段直接 400 | `apps/common/schemas.py` |
| MyBatis-Plus / JPA | Django ORM + `makemigrations` / `migrate` | 各应用 `models.py` |
| Spring Security + JWT | `JWTAuth`（HttpBearer）+ 自研 RBAC 四层校验 | `apps/common/authentication.py`、`permissions.py` |
| `@RestControllerAdvice` | `register_exception_handlers(api)` 统一转契约信封 | `apps/common/errors.py` |
| Spring 分页插件 | `paginate(request, queryset)` 输出 `{items,page,pageSize,total}` | `apps/common/pagination.py` |
| 统一响应包装 | `ok()` / `page()` / `action_result()` | `apps/common/envelope.py` |
| 幂等注解 | `guard(request, operation, object_id, payload)` | `apps/common/idempotency.py` |
| Jasypt 加解密 | AES-GCM + HMAC lookup_hash + 脱敏 | `apps/common/crypto.py` |
| POI / PDFBox | openpyxl / reportlab | 由成员3 使用 |
| MinIO Java SDK | `minio`（Python SDK） | `apps/attachments/storage.py` |
| Application Cache | `django.core.cache`（Redis 或进程内） | `config/settings.py` |

## 八、与模板的差异（重要，别照抄模板残留）

仓库里原来的 `template-django-ninja-master/` 目录**已删除**，请勿再基于它开发。采纳与改动如下：

1. 采纳：django-ninja 作为接口框架；`config/ + apps/` 分层；`Dockerfile`、`docker-compose.yml`、`deploy/nginx.conf` 已按本项目改造后并入 `backend/`。
2. 删除：`api/`（商品 CRUD 示例）、`apps/example/`、`scaffold_app.py`、`uv.lock`、模板自带的 docs 与 CLAUDE.md。
3. 版本统一：模板写的是 Python ≥3.12 + Django 3.2.24，都不可用；现已统一为 **Python 3.10.9 + Django 5.2 LTS（依赖锁 `Django>=5.2,<5.3`，实测 5.2.18）+ django-ninja 1.3.0**，并改用 `requirements.txt`（团队已用，不引入 uv）。模板里 `class PaginatedResponse[T](Schema)` 这类 3.12 泛型语法在 3.10 上会直接报错，已被移除。
   - 为什么是 5.2 而不是 4.2：4.2 LTS 的扩展支持已于 2026-04 结束，5.2 是当前 LTS（支持到 2028-04）；`Field.db_comment` / `Meta.db_table_comment` 在 4.2 与 5.2 均可用。
   - 升级已验证：同一个基座在 Django 5.2.18 下 `manage.py check` 无问题、`makemigrations --check` 无漂移、10 项接口冒烟全通过。django-ninja 1.3.0 在 5.2 上工作正常。
4. 契约适配：模板默认响应是 `{detail, code}`、分页 `per_page/total_pages`，已全部改回契约的 `{code,message,data,requestId}` + `page/pageSize`。
