## 决策 1：School、球队与 Organization 的业务编码和映射关系

**当前代码事实**（代码已核实）：
- `Organization.code`：[accounts/models.py:56](../backend/apps/accounts/models.py) CharField(64)、`unique=True`，当前仅作展示标识（`__str__`），无任何业务表引用它
- `School.code`：[persons/models.py:64-66](../backend/apps/persons/models.py) CharField(20)、可空唯一（多 NULL 合法），由调用方传入，当前**可修改**（`update_school`）
- `Team.team_no`：[teams/models.py:21](../backend/apps/teams/models.py) CharField(20)、`uk_team_no` DB 唯一；生成逻辑未实现（teams 域仅有 models）
- School/Team 与 Organization 之间**无任何 ForeignKey/OneToOne/映射表**（模型层零关联）
- `org_scope_ids` 沿组织子树收集范围（[common/scopes.py:66-73](../backend/apps/common/scopes.py)），但子树由 `Organization.id` 构成，无法落到 `base_school`/`team` 业务记录

**现存问题与影响**：学校端/球队端/市州/省级账号的数据范围只能表达为组织子树，无法解析为业务数据集合 → person/teams/materials 的 queryset 过滤无法实现；"学校端管理所属球队"的业务规则无法落地。

**方案 A（推荐）：A′-min —— org.code 承载业务编码**
- SCHOOL/UNIVERSITY 节点的 `org.code` 存 `School.code`（学校标识码）；TEAM 节点存 `Team.team_no`；省/市等上级节点维持人工编号
- 业务 code 一期不可变（见决策 2）；组织与业务记录在同一事务中创建（见决策 2 同步方式）
- 优点：零 DDL（code 列已存在且唯一）；学校标识码天然稳定；与现有子树范围机制直接衔接（org 子树 → 按 code 解析学校/球队集合）
- 缺点/风险：org.code 出现"人工编号 + 业务编码"混合语义，仅对业务节点生效，需约定文档化；code 与业务表之间无外键保障，失同步只能靠应用层校验与对账兜底；存量种子编码（PROV/CITY01/SCH001/UNI001/TEAM001/TEAM002）为 legacy 例外（见决策 7）
- 对现有代码影响：accounts 组织创建入口需加"业务节点 code 校验"（成员 2）；业务侧新增解析函数（成员 4）

**方案 B：映射表（org_id ↔ biz_type + biz_id）**
- 新建独立映射表，支持改码场景的稳定关联
- 优点：结构化、可建唯一约束、支持改码
- 缺点/风险：**新增表 = 新 DDL，冻结期内不可行**（需解冻评审）；多一张表多一条同步链路
- 对现有代码影响：新模型 + 新迁移 + 两域同步逻辑

**方案 C：org 表加 biz_ref 业务 ID 关联列**——同属改 DDL，冻结期内不可行，仅作对照，不展开。

**推荐理由**：方案 A 是唯一零 DDL 且能在冻结期内落地的结构化方案；改码需求一期关闭后，A 与 B 的能力差异消失。

**需明确回答**：
1. 是否采纳方案 A？
2. SCHOOL/UNIVERSITY 节点 org.code 是否允许为空（学校未注册组织节点时）？
3. 正式编码规则：学校标识码格式与 team_no 格式（`T+年份+8位id`？）是否按总体设计执行？

**阻塞**：决策 9 的范围实现、person/teams/materials 接口开发、组织树初始化（决策 7）。

## 决策 2：业务编码唯一性、可变性、同步方式与纠错流程

**当前代码事实**（代码已核实）：
- 唯一性：org.code 全局唯一；School.code 可空唯一（`uk_school_code`，多 NULL 合法）；team_no `uk_team_no` 唯一——DB 级约束均已冻结
- 可变性：`create_school`/`update_school`（[persons/services.py:218-249](../backend/apps/persons/services.py)）当前允许改 code；base-data 学校接口亦有对应实现与测试
- 同步：**不存在任何同步代码**（School/Team 创建不会创建组织节点）
- 纠错：无对账命令（决策 8）

**现存问题与影响**：改业务 code 会让组织节点失联（孤儿映射）；无同步则组织树永远缺失业务节点。

**方案 A（推荐）：一期业务 code 不可变 + 同进程同事务同步 service**
- 绑定组织节点后的 School.code/Team.team_no 禁改（校验放业务服务层）；改码仅限未绑定记录或走人工纠错流程（决策 8）
- 业务服务（School/Team）在同一 Django 事务中调用 accounts 提供的 `ensure_business_org` 契约创建/校验组织节点；**accounts 不 import 业务模型**，通过注册式验证器实现依赖反转（accounts 注册回调，业务域注册校验器）
- 优点：失败即整体回滚，无中间态、无孤儿；实现简单；与现有 `transaction.atomic` 风格一致
- 缺点/风险：跨域服务契约需成员 2 定义与维护；组织节点创建失败会连带业务操作失败（业务方需接受"建校必须同时能建组织节点"的强一致语义）
- 对现有代码影响：accounts 新增契约（成员 2），persons/teams 服务层调用（成员 4）

**方案 B：异步事件（outbox + 重试 + 对账）**
- 业务操作落 outbox 表，异步消费创建组织节点
- 优点：解耦、削峰
- 缺点/风险：outbox 表 = 新 DDL（冻结期内不可行）；需幂等/重试/告警/对账全套机制；窗口期内组织节点缺失 = 范围过滤漏数据，权限风险不可接受
- 对现有代码影响：新表 + 消费者 + 监控

**需明确回答**：
1. 是否接受"业务 code 一期不可变"？改码纠错走人工流程是否可接受？
2. 同步契约 `ensure_business_org` 由成员 2 实现、成员 4 调用的责任划分是否确认？
3. 建校/建队时组织节点创建失败导致业务操作整体回滚，业务上是否接受？

**阻塞**：teams 服务层实现、School/Team 接口的 code 字段策略、决策 8 对账规则。

## 决策 5：ADMIN 无组织归属与系统管理/业务数据权限分离

**当前代码事实**（代码已核实 + 实测已验证）：

- `scoped_accounts`（[services.py:149-155](../backend/apps/accounts/services.py)）L153-154 的 ADMIN 全库分支为**死代码**（空 scope 提前 return 使其不可达）
- `is_admin()` 存在但仅用于局部豁免，未用于范围策略

**方案 A（推荐）：显式管理员判定**
- `is_admin(actor)` → 全库（独立于组织树），无组织/挂根/挂非根三态统一为"业务数据全库可访问"；**无组织 ADMIN 明确允许**（初始管理员由此无需先建组织）

- 优点：可测试（独立函数+测试矩阵）、消除死代码与读写不一致、初始管理员不再依赖"先建根组织"顺序
- 缺点/风险：修改 scopes.py 属 accounts 域（成员 2）；需回归现有 accounts 行为
- 方案 B：维持"ADMIN=根子树"种子约定——不改代码但依赖种子、死代码保留、管理员创建被组织树阻塞（与决策 6 冲突）。

**需明确回答**：
1. 是否允许无组织 ADMIN？（方案 A 下默认允许）

3. 修改 scopes.py 归成员 2 还是授权协助？

## 决策 9：跨学校、跨球队与 MATCH_RECORDER 越权风险
