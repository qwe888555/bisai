## 一、统一审核职责（已批准，2026-10-28，不得列为待确认）

1. **学校端（UNIVERSITY）**：负责本校人员资格与履历材料审核，以及人员正式档案和学校归属维护。
2. **市州端（CITY）**：只审核赛事报名，不审核人员资格与履历材料。
3. **省级端（PROVINCE_REVIEWER）**：只审核赛事报名，不审核人员资格与履历材料。
4. **球队端（TEAM）**：管理本队成员关系与球队岗位，不得自行修改人员学校归属。
5. **ADMIN（系统管理员）**：
   - 账号与权限管理：负责系统账号、角色授权、账号启停及异常权限处理。
   - 组织与基础数据管理：负责组织架构、基础字典、系统配置和初始化异常的管理与维护。
   - 异常数据处理：在授权范围内处理人员档案、学校归属、球队关联、材料数据及报名数据的异常问题，并保留必要的操作记录。
   - 运行维护与审计：负责系统运行异常排查、操作日志查询、安全事件调查和数据一致性问题处理。
   - 业务审核职责边界：人员资格与履历材料由学校端审核；赛事报名由市州端和省级端按既定流程审核。ADMIN 不因系统管理身份自动替代上述角色的日常业务审核职责。
   - 业务规则约束：ADMIN 执行管理操作时，仍须遵守适用的数据归属、审核状态、版本校验、必填审核意见和审计记录规则。不得通过普通管理接口绕过必需的业务审核流程或直接伪造审核结论。
   - 特殊代审机制：如业务确需 ADMIN 代审，应另行明确适用条件、授权方式、可操作范围、审核意见、审计记录及责任追溯机制。在该机制获批准并实现之前，不默认开放代审权限。

## 一·补、球队材料与人员信息审核归属规则（已批准，2026-10-28，不得列为待确认）

### 一、运动员基本档案及学籍信息
- **审核主体：** 学校端授权审核人员。
- **审核范围：** 运动员基本档案、身份信息、学籍信息及学校归属等关键数据。
- **数据权责：** 以学校端维护的正式信息为准。球队端不得自行修改运动员的学校归属或其他学校级关键信息。

### 二、教练资格材料
- **正式审核主体：** 学校端授权审核人员。
- **审核范围：** 教练资格、相关证书及需要正式审核的资格材料。
- **设计原则：** 不默认由球队端承担正式资格审核职责，以统一审核标准，并支持教练跨球队任职或使用资格信息的业务场景。

### 三、运动员加入球队及球队成员关系
- **管理主体：** 球队端。
- **管理范围：** 本队运动员加入、退出、成员关系核验及球队内部成员管理。
- **权限边界：** 球队端可以维护本队成员关系，但不得借此变更运动员的身份、学籍或学校归属。

### 四、球队自身业务材料
- 球队端负责球队材料的提交、维护和补充。
- 球队材料是否需要正式审核，应按照材料类型配置及相应业务流程执行。
- 对于球队荣誉等需要审核的材料，应明确学校端授权审核人员的正式审核职责；其他材料按照已批准的材料类型审核配置执行。
- 球队端的材料维护权限不自动等于正式审核权限。

### 五、系统管理员权限
- ADMIN 的系统管理身份不自动授予普通业务审核权。
- 如需管理员参与普通材料审核，应有明确的权限授权规则。
- 异常材料处理应采用独立、受控且可审计的管理流程，不与常规业务审核混为一体。

### 六、权限实施要求
所有接口必须同时校验角色权限和数据范围。前端隐藏按钮不能替代后端权限控制；不得因球队端能够维护材料，就允许其审核学校级资格信息或修改学校归属。

## 一·补二、省级分层复核与批次审核规则（业务规则候选，2026-10-30）

> 本节为 2026-10-30 项目负责人业务意见整理的**业务规则候选方案**。
> - "核心原则"已由项目负责人确认；
> - 抽查比例、批次审批规则、异常件分类、普通件豁免等具体规则标注为**候选**或**待裁定**，尚未正式批准；
> - 不代表代码实施、数据库变更或生产上线授权；
> - 不得将"候选方案""建议方案"写成"已批准""已生效"。

### 0. 核心原则（已确认，2026-10-30）

1. 在保障人员资格、审核质量和责任可追溯的前提下，提高省级审核效率。
2. 异常件必须逐件审核，不能因为采用抽查或批次审批而绕过异常审核。
3. 批次审批是批量执行审核动作，不是降低单条记录的审核标准。
4. 普通件是否可以免于省级逐件复核，必须在异常件规则、抽查机制和质量评估基础上另行决定。
5. 如后续临时想法与上述已确认原则冲突，优先按已确认原则整理方案；最终裁定权属于项目负责人。

### 1. 省级抽查比例（候选测算起点，待裁定）

**1.1 候选比例**
- **10% 作为普通件省级抽查比例的候选测算起点**。
- 此比例**不是已批准的正式比例，也不是已生效规则**。

**1.2 计算分母**
- 抽查比例的分母 = 具体审核周期、赛事或报名批次中**符合抽查条件的普通件数量**。
- 学校总数（约 8,700 所）**不得**直接作为抽查比例的计算分母。

**1.3 排除范围**
- 异常件**不纳入**普通件抽查比例，必须逐件审核（见第 3 节）。

**1.4 抽样方案候选要求**
- 按市州分层，避免抽查过度集中在少数市州；
- 在条件允许时考虑学校、赛事类别和参赛类别的覆盖；
- 分层后随机抽取，明确抽样记录和重复抽样处理；
- 抽查发现重大问题或系统性错误时，触发扩大核查，必要时恢复相关范围的逐件审核。

**1.5 待技术负责人评估并提供数据的参数（不得凭经验直接确定）**
- 各市州最低抽查量；
- 错误率阈值；
- 扩大核查比例；
- 正式试运行比例。
- **所需收集的数据**：各市州退回率、纠错率、资格问题发生率、材料问题分布、普通件数量、省级实际审核能力。

### 2. 批次审批：市州与省级均采用整批失败原则（业务规则候选）

> 批次审批是批量执行审核动作，不降低单条记录的审核标准。
> **适用范围**：批次审批仅适用于符合条件的普通件；异常件（见第 3 节）不得混入普通件批次，应单独进入逐件审核通道。
> **整批失败规则**：批次中任何记录校验失败，本次批次整体不生效，不允许部分记录通过；需逐条检查并修正后重新提交。不得改成部分成功。

**2.1 市州批次审批**
- 例：一批 100 条记录中有 3 条校验失败：
  - 本次批次审批**整体失败**，100 条记录均不得因本次批次操作而被自动审批通过；
  - 系统返回失败记录及具体原因；
  - 必须逐条检查整批 100 条记录，修正问题并完成必要复核后，才能重新提交批次审批；
  - 保留批次操作、失败原因、操作者、时间和重新提交记录。

**2.2 省级批次审批**
- 例：一批 100 条记录中有 2 条校验失败：
  - 本次批次审批**整体失败**，100 条记录均不得因本次批次操作而被自动审批通过；
  - 系统返回失败记录及具体原因；
  - 必须逐条检查整批 100 条记录，确认问题范围并完成必要复核后，才能重新提交审批；
  - 如果失败暴露出市州初审的系统性问题，应评估是否需要扩大核查；
  - 保留批次失败、复核、再次审批和最终处理结果的审计记录。

**2.3 技术实现要求（候选，待技术负责人评估）**
- 整批失败必须是真正的**原子性操作**，不允许部分记录已审批通过、随后又将整批标记为失败；
- 需评估"先完成整批校验，再统一写入审批结果"的方案，明确事务、一致性、并发修改和重复提交的处理方式；
- 不得仅依赖前端提示来保证整批失败；
- 技术负责人可提出实现方案，但不得自行改变整批失败业务原则。

### 4. 普通件是否免于省级逐件复核（待裁定，分阶段方案）

**当前阶段**
- 维持现有**两级逐件审核**要求：市州初审（`PENDING_CITY_REVIEW` 阶段）→ 省级终审（`PENDING_PROVINCE_REVIEW` 阶段），不引入抽查或豁免。
- 先完善异常件规则（第 3 节）并完成抽查方案测算（第 1 节）。
- 历史 `subject_type=CITY` 报名的直省审路径属历史数据兼容问题，其业务规则适用范围与处置方式**待项目负责人另行确认**；本轮不决定其是否适用新分层规则，不改变历史数据或审核流程。

**试运行阶段**
- 只有在项目负责人**另行批准试运行范围和方案**后，才可在批准范围内开展试运行。
- 试运行不得擅自改变现有审批责任。

**评估阶段**
- 根据抽查发现的问题、纠错情况、扩大核查次数、市州审核质量和省级工作量，形成评估报告。
- 由项目负责人决定是否允许普通件免于省级逐件复核。

**两种模式的责任划分（必须明确区分，不得混为一谈）**

| 模式 | 含义 | 责任划分 |
| --- | --- | --- |
| A | 省级不再逐条复核，市州审核结果直接生效 | 市州承担最终审核责任；省级不签字 |
| B | 省级保留最终审批权，只是不再重复逐条检查所有材料 | 省级仍承担最终审批责任；抽查/批次发现问题仍可阻断 |

**条件性豁免的前置要求（如未来考虑，须先提出并待裁定）**
- 适用范围；
- 质量门槛；
- 暂停条件；
- 恢复逐件审核的触发条件；
- 责任追溯方式。

### 5. 项目团队职责分工（2026-10-30 明确）

> 表中角色为**职责划分**，不要求小团队配置同等数量的独立人员；允许同一人员合理兼任多个角色。但高风险操作、涉及冻结表或难以回滚的变更，必须按风险要求执行**独立复核**——不得将自我检查标为独立复核。

| 角色 | 职责 |
| --- | --- |
| **项目负责人** | 决定正式抽查比例、异常件规则、批次审批政策、普通件豁免政策及试运行范围 |
| **业务负责人** | 整理业务场景、异常分类、审核责任和处理流程，提交候选方案 |
| **技术负责人** | 检查现有实现，测算工作量与风险，提出技术方案、改动范围和测试要求；不得替代项目负责人决定业务政策 |

| **运维人员** | 提供部署、监控、数据安全和执行记录；须取得相应授权后方可操作 |

### 八.1 材料审核状态进入报名校验（阶段一 8 条批准口径终态）

**批准口径（2026-10-31）：**
1. 双条件设计：报名附件证据与材料域审核通过证据**分别校验，互不替代**；
2. 仅对 requiredMaterialTypes 与材料域字典交集中 need_audit=true 的类型做审核状态校验
   （当前唯一交集=STUDENT_STATUS）；
3. PENDING、REJECTED、DRAFT、WITHDRAWN 均不算审核通过；
4. 提交预检 WARNING；终审对已查明但未通过审核的材料 ERROR 阻断；
5. 查询不到记录或查询异常遵循降级口径：不臆造缺失，也绝不视为审核通过；
6. 不消费 is_required，不修改模型默认值，不改变 P2 口径；
7. material_batch_query 先审查并单独稳定，再接入报名域（5b4d022 / dc19c13）；
8. 本轮只处理 PERSON 侧，不修改 TEAM 映射（TEAM 类型由 applies_to 预检自然降级跳过）。

**边界行为四情况表**（以 e76033d 实施与测试为准，precheck.py `_material_audit_snapshot`）：

| 情况 | 行为 |
| --- | --- |
| 报名名单没有必需附件 | MISSING_MATERIAL ERROR，阻断提交与终审（附件存在性门槛，原口径不变） |
| 材料域查询成功，但该类型无审核记录 | 系统已确认材料域未返回该类型审核记录；按口径#5 降级：不臆造缺失、不阻断、不视为 APPROVED |
| 材料域查询失败、依赖不可用或查询异常 | **未成功获得材料域数据，不能证明记录存在，也不能证明不存在**；同按口径#5 降级 |
| 材料域记录存在但状态非 APPROVED | 预检 QUALIFICATION_PENDING WARNING；终审 ERROR 阻断 |

上下文差异），§2 层合并产生同一条"暂无可查询的履历材料"WARNING——如实记录，不补造区分。

**类型归属两分法**：① 报名域已定义的附件类型但不属材料域审核字典（如 STAMPED_FORM）→
按报名附件证据契约处理，不要求审核状态；② 报名域也不认识的完全未知 code → 终审
fail-closed（方案 B 口径）。不是"所有不在字典的类型都无条件通过"。

**待复核的边界问题（待产品裁定，非已确认缺口）**：情况 2（从未上传履历材料者）终审不因
审核状态阻断，是口径#5 批准的降级行为；是否应升级为 fail-closed 需另行提出产品变更。

实现位置：enrollments/precheck.py `_material_audit_snapshot` + 预检 §2.5 + 终审硬门槛；

   若多个账号参与同一材料经办，应由未参与经办的其他 UNIVERSITY 账号审核；学校须合理安排
   材料经办流程，必要时配置第三个账号。本条为按防自审机制推导的运营要求，**不据此修改
   防自审代码或改变既有证据集**；
3. 不拆分独立"学校审核员"角色，维持现有 UNIVERSITY 单角色（UNIVERSITY 常量为系统兼容

6. 两域防自审 B 口径均予追认且**不统一证据语义**：persons（person.create + person.self_confirm，
   最近提交者语义）与 materials（material.create + material.update，任一经办者语义；remove
   不纳入——软删后不可审）各自维持证据集、SUCCESS 限定、缺日志放行边界（无证据可判≠绕过，
   数据范围/状态机/乐观锁/留痕全保留）、事务行锁顺序（查询在 select_for_update 获锁后）。
